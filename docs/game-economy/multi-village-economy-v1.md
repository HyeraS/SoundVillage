# SoundVillage 다중 마을 경제·상품 계약 v1

상태: 런타임 구현 승인 계약. `data/economy/catalog-v1.json` 스키마 버전 1.1.0과 이 문서가 단일 기준이다. 실제 런타임, DB 마이그레이션, 구매 API, UI 변경은 이 개정의 범위가 아니다.

## 제품 목표와 범위

경제의 목적은 Animal, Human, Nature, Urban, Music, Lab의 소리를 골고루 전사하도록 유도하는 것이다. 일반 상품 하나를 사려면 서로 다른 네 마을 화폐가 필요하며, 희귀·이벤트 상품, 애니메이션 상품, 펫, 테마 세트만 여섯 마을 화폐를 요구할 수 있다.

의상과 인테리어는 특정 마을 소유가 아닌 통합 상점 상품이다. 마을 정체성은 가격의 여섯 화폐 벡터에만 존재한다. 화폐 교환, 선물, 참가자 간 시장은 제공하지 않는다.

## 정규 보상 계약

| 행동 | 지급량 | 지급 지갑 |
| --- | ---: | --- |
| 유효한 새 전사 | 5 | 제출한 소리의 마을 |
| 유효한 새 투표 | 2 | 원본 소리의 마을 |
| 건너뛰기 | 0 | 없음 |
| 특정 표현 사용 | 추가 보상 0 | 없음 |
| 다른 참가자와 일치 | 추가 보상 0 | 없음 |

중복 요청은 동일한 결과를 반환해야 하며, 배정된 오디오 하나당 유효 결과 하나라는 기존 경계를 유지한다. 클라이언트가 보상 마을이나 금액을 결정해서는 안 된다.

## 지갑과 가격 스키마

정규 지갑 순서는 다음과 같다.

```text
[Animal, Human, Nature, Urban, Music, Lab]
```

카탈로그와 API는 여섯 키를 모두 가진 명명 객체를 사용한다. 0인 지갑도 생략하지 않으며 위치 기반 숫자 배열은 영속화하지 않는다.

```json
{
  "Animal": 5,
  "Human": 5,
  "Nature": 5,
  "Urban": 5,
  "Music": 0,
  "Lab": 0
}
```

### 일반 상품 A–F 조합

| 조합 | 필요한 지갑 |
| --- | --- |
| A | Animal, Human, Nature, Urban |
| B | Human, Nature, Urban, Music |
| C | Nature, Urban, Music, Lab |
| D | Urban, Music, Lab, Animal |
| E | Music, Lab, Animal, Human |
| F | Lab, Animal, Human, Nature |

일반 유료 상품은 정확히 네 지갑을 사용한다. 전체와 가격 등급뿐 아니라 `productGroup`이 `outfit`, `accessory`, `interior`인 각 주요 상품군에서도 A–F 최다·최소 사용 수 차이는 1 이하여야 한다. 새 상품은 이 조건과 마을별 총수요 허용 오차를 함께 만족하는 배치로 추가한다.

### 가격 등급

| 등급 | 벡터 규칙 | 합계 | 전사 보상 환산 | `minimumFreshAnnotationCount` |
| --- | --- | ---: | ---: | ---: |
| Small | A–F 네 지갑에 3/4/4/4 | 15 | 3 | 4 |
| Standard | A–F 네 지갑에 각각 5 | 20 | 4 | 4 |
| Premium | A–F 네 지갑에 각각 10 | 40 | 8 | 8 |
| Rare/event/pet/animated | 여섯 지갑에 각각 10 | 60 | 12 | 12 |
| Theme set | 여섯 지갑에 각각 15 | 90 | 18 | 18 |

`estimatedAnnotationCount`는 `sum(cost) / 5`인 가격 환산치다. Small 상품의 UI 설명은 “전사 3회”가 아니라 **“서로 다른 4개 마을에서 각각 한 번 이상 참여”**로 고정한다. 15라는 가격 합계와 새 지갑에서 필요한 최소 참여 횟수 4를 혼동하지 않는다.

## Character v2 의상 계약

`basic`은 무료 기본 의상이다. 이를 제외한 원본 마스터 18종은 모두 유료 카탈로그에 등록한다. 원본은 `assets/Character v.2/clothes/*`를 직접 참조하며 복사하거나 수정하지 않는다. 아직 연결되지 않은 의상은 `plannedRuntimeAsset`만 기록한다.

| 구분 | 상품과 조합 |
| --- | --- |
| A 일반 | `overalls`, `floral` |
| B 일반 | `sailor`, `dress` |
| C 일반 | `sporty`, `pants`, `pants_suit` |
| D 일반 | `suit`, `sailor_bow` |
| E 일반 | `shoes`, `skirt`, `skull` |
| F 일반 | `spaghetti`, `stripe` |
| ALL 희귀·이벤트 | `witch`, `clown`, `pumpkin`, `spooky` |

일반 의상 조합 수는 A–F 순서로 2/2/3/2/3/2이며 최다·최소 차이는 1이다. 기존 인기 의상 `overalls`, `sailor`, `sporty`, `suit`도 서로 다른 A–D에 배치해 특정 조합에 몰리지 않게 했다. ALL은 `witch` 희귀 의상과 명시적인 이벤트 의상 세 종에만 사용한다.

## 출석 보상

출석 보상은 유지하며 참가자별 주간 셔플을 사용한다.

- 주차 키는 기존 실험 날짜 규칙과 같은 `Asia/Seoul` 기준 월요일 00:00에 시작하는 ISO 주를 사용한다.
- 1–6일차에는 여섯 마을의 순열을 한 번 생성한다. 각 마을은 정확히 한 번 등장하며 지급량은 순서대로 2, 2, 2, 3, 3, 4다.
- 순열은 서버 비밀을 사용하는 버전 고정 HMAC과 `participant_id + week_key`로 결정하고, 최초 지급 전에 저장한다. 같은 참가자·주차에는 항상 같은 순열을 반환한다.
- 7일차에는 첫 유효 청구 시점의 현재 잔액이 가장 낮은 마을에 5를 지급한다. 동률 후보는 서버의 버전 고정 HMAC으로 하나를 결정하고 결과를 저장한다.
- 주간 합계는 `2 + 2 + 2 + 3 + 3 + 4 + 5 = 21`이다.
- 청구 멱등성 키는 `participant_id:week_key:attendance_day`다. 새로고침, 재전송, 동시 요청은 저장된 동일 결정을 반환하며 화폐를 다시 뽑거나 중복 지급할 수 없다.

클라이언트가 순열, 7일차 최저 지갑, 동률 결과를 제출하는 인터페이스는 금지한다. 서버는 결정 저장과 원장 지급을 한 트랜잭션 경계에서 처리해야 한다.

## 오늘의 특가

오늘의 특가와 할인 규칙은 v1 경제 계약에서 제거한다. `catalog-v1.json`에는 daily-deal 또는 discount 필드를 두지 않으며 검증기가 해당 필드의 재도입을 실패 처리한다. 현재 레거시 런타임의 특가 코드는 이번 문서·계약 개정에서 수정하지 않지만, v1 런타임 전환 시 호출과 UI 노출을 제거해야 한다.

## 테마 세트

테마 세트는 다음 두 경로를 구분한다.

### 세트 일괄 구매

- `bundlePurchasePolicy`가 구매 조건을 정의한다.
- `bundleItemIds` 중 보유 항목이 0개일 때만 일괄 구매할 수 있다.
- 하나라도 보유하면 구매를 차단하고 구성품별 수집 진행도를 표시한다.
- 일괄 구매는 세트 가격을 한 번 원자적으로 차감하고 구성품을 영구 해금한다.

### 개별 수집 완성 보상

- `collectionCompletionReward`가 일괄 구매와 별개의 무료 보상을 정의한다.
- 모든 구성품을 개별 획득해 완성한 경우에만 계정당 한 번 지급한다. 세트 일괄 구매는 이 보상의 트리거가 아니다.
- 보상은 상점에서 판매하지 않으며 서버가 `account_id + rewardId` 기준으로 멱등 지급한다.
- 현재 세 세트의 보상 에셋은 미확정이다. 각 레코드는 `placeholder_completion_asset_<set_id>`를 사용하고 `assetSelectionRequired: true`로 둔다. 임의 에셋을 확정하지 않는다.

## 집 꾸미기 공식 시스템

`InteriorDecorRoom`이 유일한 공식 집 꾸미기 시스템이다. `HouseDecorRoom`은 삭제하지 않지만 테스트 전용·비공식으로 취급한다.

- 가구 구매는 `item_id`별 영구 해금이다.
- 해금한 가구는 같은 방에 여러 번 배치할 수 있다. 배치 인스턴스는 별도 레코드여도 소유·수집·친구 초대 조건에서는 고유 `item_id` 하나로 계산한다.
- 자동 생성 House 상품 8,457개는 공식 상점에서 숨긴다.
- 현재 선택된 House 애니메이션·문·펫 6개는 `officialStoreStatus: pending_interior_review`다. `decorSystemPolicy.houseToInteriorReviewMappings`가 같은 ID를 유지한 Interior 대상 매핑을 기록하고, `futureCategoryMappings`는 TV·벽난로·조명·문을 `animated_furniture`, 펫을 `pet`으로 검수 후 편입하는 범주 계획을 정의한다.
- 검수 항목은 소스 권리/출처, 프레임·타이밍, 충돌/점유 크기, 미리보기, 모바일 성능, 펫 행동이다. 승인 후 공식 Interior 카탈로그로 편입한다.
- 두 시스템의 DB나 상품 ID를 지금 합치거나 삭제하지 않는다. 후속 마이그레이션은 기존 ID 매핑, 소유권 중복 제거, 배치 인스턴스 변환, 검증·롤백 순서로 별도 설계한다.

## 정식 실험 시작 시 지갑 정책

실제 실험 전 테스트 데이터만 있다고 가정한다.

- 기존 단일 잔액은 여섯 지갑으로 분배하거나 복원하지 않는다.
- 정식 실험 시작 경계에서 모든 참가자의 여섯 마을 지갑을 각각 0으로 초기화한다.
- 기존 단일 잔액과 관련 원장은 즉시 삭제하지 않고 읽기 전용 감사·롤백 스냅샷으로 보존한다. 스냅샷 생성과 검증이 성공한 뒤에만 새 지갑을 활성화한다.
- 이 정책만으로 보유 아이템, 세트 구성품 소유권, 방 배치 데이터는 초기화하지 않는다.
- 본 개정에서는 실제 초기화 SQL이나 마이그레이션을 실행하지 않는다.

## 구매·소유권 원칙

- 서버가 카탈로그 ID로 가격 벡터와 지급 항목을 해석한다. 클라이언트 가격은 무시한다.
- 구매는 여섯 잔액 잠금, 전체 벡터 검증, 비영(非零) 지갑 차감, 영구 소유권 지급, 원장 기록을 하나의 DB 트랜잭션으로 처리한다.
- 부분 차감, 지갑별 재시도, 중복 소유권 지급은 금지한다.
- 의상·액세서리·인테리어 소유권은 비스택형이다. 반복 배치는 소유 수량이 아니라 배치 인스턴스다.

## 후속 구현 경계

이미 적용된 역사 SQL은 수정하지 않고 새 forward migration을 만든다. 후속 구현은 여섯 지갑과 벡터 원장, 전사·투표·출석 지급, 원자적 구매, 테마 완성 보상, 공식 Interior 소유권, 감사 스냅샷, RLS와 동시성 테스트를 포함해야 한다.

이 계약 개정에서는 다음을 하지 않았다.

- 런타임·DB·구매 API·UI 구현
- 실제 참가자 잔액 초기화 또는 데이터 마이그레이션
- 원본 에셋 수정이나 `public` 대량 복사
- House/Interior DB 및 ID의 파괴적 병합

## 아직 남은 제품 결정

1. 세 테마 세트의 무료 완성 보상 에셋 선정. 선정 전에는 placeholder와 `assetSelectionRequired`를 유지한다.
2. 검수 대기 House 후보 6개의 공식 Interior 편입 승인 여부와 펫 동작 사양.
3. 정식 실험 시작 시각과 보존 스냅샷의 보관 기간·접근 권한. 초기값 0, 비분배, 소유·배치 유지 원칙은 이미 확정됐다.
4. Character v2 의상별 팔레트 해금 범위. v1 가격 계약은 스타일 단위이며 원본 팔레트 파일을 변경하지 않는다.
